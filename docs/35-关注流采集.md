# 关注流采集（动态采集方式）

> 状态：**已并入主循环**（2026-11-08）。默认 `poll.mode=auto`：有 `SESSDATA + bili_jct`
> 就走关注流，没有就自动退回逐人轮询。实验过程与数字见

## 1. 换掉了什么

| | 逐人轮询（旧） | 关注流（新） |
|---|---|---|
| 请求 | 每个主播一次，29 个号一轮 29 次 | 一次 `feed/all` 拿回全部关注的新动态 |
| 单轮耗时 | 32~34 秒（受 1.2s 节流与并发上限约束） | 稳态 191~262 ms，冷启约 2.3 s |
| 单轮流量 | 29 份 JSON | 单页约 200 KB（60 秒一轮约 310 MB/天） |
| 覆盖面 | 只看名单内 | 关注的全部号（名单外自动忽略） |
| 召回 | 完整（只要你请求了） | 受窗口 / 页数限制，需低频补漏兜底 |

换过去后，**名单里新增一个号不用再改轮询参数**：账号先关注它（关注同步会自动补），
下一轮关注流就会带上它的动态。

## 2. 原理

1. `GET https://api.bilibili.com/x/polymer/web-dynamic/v1/feed/all`
   参数 `type=all&features=itemOpusStyle&timezone_offset=-480&page=N`，带 WBI 签名与登录 Cookie；
2. **必须登录**：未登录拿到的是推荐流（会混进名单外内容），不能当关注流用；
3. 单页固定 20 条，`data.offset` 是下一页游标；
   `update_num` 恒为 0、`has_more` 有数据时恒为 true，**不能靠它们判断翻到哪**；
4. 翻页终止条件（`core/feed_collect.py: feed_round_once`）：
   - 见到上一轮已经处理过的动态 id（`known_ids`，取各号状态的 `last_dynamic_id`）→ 停；
   - 翻到 `feed_pages` 页上限 → 停；
   - 当前页最旧一条已经早于「名单内最新水位」（`since_ts`）→ 停；
   - 没有更多数据（`has_more=false` / 空页）→ 停；
5. 首页条目数达到 `feed_burst_threshold`（默认 15）时，说明积压了，页数上限放宽到
   `feed_burst_pages`（默认 3），一次多翻几页；
6. 取回后按 `module_author.mid` 分组，**只处理监控名单里的 uid**，其余直接丢弃（不落库、不推送）。

## 3. 三种取数方式

| `poll.mode` | 行为 | 需要的凭据 |
|---|---|---|
| `auto`（默认） | 有 `SESSDATA` + `bili_jct` 走关注流，否则逐人轮询 | 可选 |
| `feed` | 强制关注流；凭据不全时**告警并临时退回逐人轮询**，不会一条都收不到 | `SESSDATA` + `bili_jct` |
| `per_user` | 强制逐人轮询（老的 29 次请求方式） | 无 |

凭据在 `config/bili_follow.env`（`SESSDATA` + `bili_jct`）。
扫码生成：管理台「B 站登录态」卡点扫码，或 `python scripts/follow_feed_login.py`。
**`bili_jct` 是写操作（关注）的 CSRF token，无法从 `SESSDATA` 推导，必须单独拿到。**

## 4. 配置

`config/subjects.json` 的 `poll` 块：

```json
{
  "poll": {
    "mode": "auto",
    "live_interval_s": 45,
    "dynamic_interval_s": 240,
    "feed_interval_s": 60,
    "feed_pages": 3,
    "feed_burst_threshold": 15,
    "feed_burst_pages": 3,
    "sweep_hours": 6,
    "sweep_max_age_min": 720,
    "sweep_push_late": true,
    "sweep_late_max": 30,
    "follow_sync": true,
    "follow_sync_hours": 6
  }
}
```

| 键 | 默认 | 说明 |
|---|---|---|
| `mode` | `auto` | `auto` / `feed` / `per_user`，见上一节 |
| `feed_interval_s` | 60 | 关注流轮询间隔（feed 模式下覆盖 `dynamic_interval_s`） |
| `feed_pages` | 3 | 单轮最多翻几页（3 页 = 60 条） |
| `feed_burst_threshold` | 15 | 首页条目数达到多少算「积压」 |
| `feed_burst_pages` | 3 | 积压时放宽到的页数上限 |
| `sweep_hours` | 6 | 低频补漏间隔（小时）；**设 0 关闭** |
| `sweep_max_age_min` | 720 | 补漏回看窗口（分钟，默认 12 小时）；更早的「新发现」条目只记已见 |
| `sweep_push_late` | true | 补漏补到的遗漏动态是否推送；false 退回旧行为（比水位旧的条目一律不推） |
| `sweep_late_max` | 30 | 单次补漏最多补推多少条，超出只记已见（防停机重启后刷屏） |
| `follow_sync` | true | 启动时与每 N 小时把名单里没关注的号补关注 |
| `follow_sync_hours` | 6 | 关注同步间隔 |
| `live_interval_s` | 45 | 直播轮询（与取数方式无关） |
| `dynamic_interval_s` | 240 | 逐人轮询间隔（`per_user` 模式才用） |

命令行可临时覆盖：`python scripts/run_bot.py --poll-mode feed|per_user|auto`。

## 5. 去重、水位与推送口径

关注流、逐人轮询、补漏三条路径共用 `core/watcher.py: _digest_items`，规则只有一份：

- **基线轮**（该号没有状态）：只 `mark_seen` + 记水位，不推送；
- 已读表：`seen_dynamic(uid, id_str)`，只回看最近 90 天；
- **置顶的旧动态**（`pub_ts <= 水位`）：跳过，不推；补漏（`sweep_push_late=true`）走同一函数但
  `ignore_watermark=True`——漏掉的条目常比水位旧，不忽略水位就永远补不回来（2026-11-11）；
- 该号关了「动态推送」：照常记已见、水位前进，但不产事件；
- 早于 `sweep_max_age_min`（默认 12 小时回看窗）的「新发现」条目：只记已见，不推送；
- 比水位旧、但在回看窗内的补漏条目：**照常推送**（`sweep_push_late`），单次受 `sweep_late_max` 限制。

## 6. 关注同步（只关注，不取关）

`core/feed_collect.py: follow_sync`：

- 取自己的关注列表（`x/relation/followings`）与监控名单做 diff；
- 缺的补关注（`x/relation/modify` + `csrf=bili_jct`，间隔 2 秒）；
- **永不自动取关**：取关会改变账号的社交关系，且补漏仍能抓到，没必要冒这个风险；
- 结果落 `logs/follow_sync/follow-sync-YYYYmmdd-HHMMSS.json`（只在真的有关注/失败时写），
  需要回滚可照 journal 逐条取关，或跑 `python scripts/probe_follow_feed.py restore`；
- 没有 `bili_jct` → 跳过并记一句日志，不影响取流；
- 管理台「动态采集方式」卡上的「同步关注」按钮 = 写 `data/follow_sync.request`，
  采集进程下一轮执行。

### 6.1 名单外自动忽略（2026-11-10）

「关注了谁」是 B 站账号的状态，「监控谁」只认监控名单（管理台 / `config/subjects.json`），两者允许不一致：

- **取流时**：按 `module_author.mid` 归并后，只处理库里启用的 subject；名单外的条目只计入
  `feed_last_ignored`，不落库、不推送。管理台「动态采集方式」卡显示「（名单内 X 条，名单外忽略 N 条）」。
- **启动对账**：`Watcher.init_subjects` 在 upsert 名单后调用 `_reconcile_subjects`——名单内一律启用、
  名单外一律**停用**（`Store.set_subject_enabled`，不删除），日志打
  `[名单] 停用 N 个不在监控名单里的号：名字(uid)`；重新加回名单，下一次启动打
  `[名单] 恢复 M 个重新加入名单的号：…`。停用只是不取数、不推送，`subject_state` 的水位与推送开关都保留。
  这是**系统对账**，不是用户开关：管理台自 2026-11-10 起已移除手动启用 / 停用，名单里所有号一律轮询。
- **镜像只写启用行**：`_sync_config_subjects` 以 `WHERE enabled=1` 读库重建 `config/subjects.json`，
  停用行不写进镜像。否则「停用 → 镜像带回 → 下次启动当成名单 → 再启用」会形成回环
- **旧镜像的 `_disabled`**：2026-11-10 之前管理台停用会在镜像里写 `_disabled`；新版本不再写、也不再读这个标记
  （`enabled` 只表示「是否在名单里」，下次回写镜像时清掉旧标记）。`_no_room` 只表示没有直播间，不算停用。
- **为什么不能只依赖 B 站关注列表**：关注同步只关注、不取关（§6），用户也可能在 App 里关注名单外的人；
  名单对账保证「关注多少」不会变成「推送多少」。

## 7. 低频补漏（sweep）

关注流有窗口与页数上限，不能保证 100% 召回：

- 每 `sweep_hours`（默认 6 小时）逐人抓一次（并发 5、带节流），把关注流没带到的条目补上；
- **补到的遗漏动态照常推送**（`sweep_push_late=true`）：关注流一轮会把水位顶到同批最新条目，
  被吞掉的条目 `pub_ts` 往往**比水位还旧**，所以补漏必须忽略水位（`ignore_watermark`）才补得回来；
- 两条防刷屏：① 只看最近 `sweep_max_age_min`（默认 720 分钟 = 12 小时），更早的只记已见；
  ② 一次最多补推 `sweep_late_max`（默认 30）条，按发布时间正序推最新的这一批，其余只记已见；
- 想回到「补漏只标已读」的旧口径：`sweep_push_late: false`（此时回看窗仍按 `sweep_max_age_min`）；
- 关注同步与补漏都在**后台任务**里跑（`_spawn`），不阻塞直播轮询；
- 压测期在大关注面（101 人）下用逐人真值对照，曾记录到窗口内缺 23/140（16.4%）的样本，
  与早期 27 人时期 60/60 的结论不一致；结项结论是「没测出问题 ≠ 证明没问题」，
  所以默认保留补漏，**不需要可以设 `sweep_hours: 0`**。

## 8. 管理台

概览页「动态采集方式」卡（`GET /api/feed/status`）：

- 徽标：关注流 / 逐人轮询；下拉可直接切换 `poll.mode`（**改完需重启采集进程**，卡上有提示）；
- 最近一轮：页数 / 条目 / 名单内命中 / 耗时 / 流量 / risk；
- 累计：轮次、失败次数、最后一次错误；
- 补漏：上次时间、累计轮次、累计**补到并推送**条数、单次上限；关注同步：上次时间、关注数、计划/新增/失败；
- 三个按钮：**立即取流**、**立即补漏**、**同步关注**（走 `data/*.request` 文件，
  采集进程下一轮消费；`sweep_hours=0` 时「立即补漏」会被忽略并打日志）。

## 10. 迁移与回滚

**切到关注流**（新装默认 `auto`，有凭据即生效）：

1. 管理台扫码登录（或 `python scripts/follow_feed_login.py`），确认 `config/bili_follow.env`
   里既有 `SESSDATA` 也有 `bili_jct`；
2. `config/subjects.json` 里 `poll.mode` 写 `auto` 或 `feed`；
3. 重启采集进程（管理台「重启采集」按钮，或写 `data/restart.request`）；
4. 看日志：`[取数] 动态采集：关注流…` 与 `[关注流] N 页 M 条（名单内 K）→ 新增 X 条`。

**回滚到逐人轮询**：`poll.mode` 改 `per_user`（或启动加 `--poll-mode per_user`）→ 重启。
两条路径的数据表完全一致（`seen_dynamic` / `subject_state`），切换不需要迁库。

## 11. 风险与限制

1. 关注流是**平台推荐/聚合口径**，接口字段说变就变；取流失败只记 meta 并跳过该轮，
   不会带崩主循环，但会一直取不到数据 —— 监控「失败次数」应常态化；
2. 窗口有限（约 60 条 / 2 天），长时间停机后首轮只能补到窗口内的部分，重启后建议先跑一次补漏；
3. 名单里没关注的号**不会**出现在关注流里（`follow_sync` 会补，但需要 `bili_jct`）；
4. 关注是写操作，会让账号的关注列表变长；不自动取关，要清理自己动手；
5. 关注上限 2000 人；名单到几百人时注意 `feed_pages` 与补漏耗时；
6. `bili_jct` 与 `SESSDATA` 同生命周期，重新登录后要重新扫码；
7. 仍有风控可能：沿用客户端的 0.3 s 重试；关注流没有 desktop 等价端点，失败即回落逐人那一轮；
8. **SESSDATA 过期会自动退回逐人轮询**：`feed/all` 返回 `-101`（未登录）时记一次「[关注流] B 站登录态失效 → 回退逐人轮询（动态照常收，只是慢一些；续期成功会自动切回关注流）」，然后 `feed_enabled()` 直接返回 False，本轮之后的动态照常按人抓、不再每轮拿 -101 空转；重新扫码后登录态恢复，下一次检测自动切回关注流。

## 12. 排错

| 现象 | 先看什么 |
|---|---|
| 一直「逐人轮询」 | `config/bili_follow.env` 是否有 `SESSDATA` 与 `bili_jct`；日志里的 `[取数]` 行；看到「登录态失效 → 回退逐人轮询」就是 `SESSDATA` 过期了，重新扫码即可 |
| 关注流 0 条 | 是否未登录（拿到的是推荐流）、关注列表是否为空、`feed/all` 是否被风控 |
| 有动态但不推送 | 该号「推送」列的动态开关是否关掉；条目是否早于水位（置顶）或早于补漏回看窗 |
| 补到但没有推送 | 先看 `sweep_push_late` 是否为 false、条目是否早于回看窗（默认 12 小时）、是否被 `sweep_late_max` 截断（日志有「超过单次上限」一行） |
| 切换 mode 不生效 | 改的是 `config/subjects.json` 还是管理台？两者都要重启采集进程 |
| 关注同步失败 | 多为 `bili_jct` 失效（-352 / -412），重新扫码；失败不取关、不改名单 |
