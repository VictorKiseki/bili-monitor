# 开源发布清单

这条分支（`opensource`）是面向公众的发布线：**MIT 许可**、干净历史、开源协作文件齐全。
它和开发线 `master` 没有共同祖先（见 §9），所以下面几件事只在第一次发布时做一次。

## 1. 发布前本地核对

```powershell
git status                     # 必须在 opensource 分支且工作树干净
.\runtime\python.exe scripts/run_tests.py
.\runtime\python.exe scripts\release.py check
git log --oneline              # 只有发布快照（3 条），历史里不该出现真实凭据
```

## 2. 建远程仓库

本项目发布在 **Gitee 私有仓库** `victorkiseki/bili-monitor`：`origin` = `git@gitee.com:victorkiseki/bili-monitor.git`（SSH 公钥已配置）。
换账号或换仓库时才需要重建：在 Gitee 新建**空**仓库，**不要**勾选「使用 Readme 初始化 / .gitignore / 开源许可证」，否则首推会冲突。

## 4. 推送

```powershell
git remote add origin git@gitee.com:victorkiseki/bili-monitor.git
git push -u origin opensource
git push origin v0.1.0 v0.3.0     # 显式列 tag；--tags 会把 v0.1.0-personal 一起推上去
```

推完在 Gitee 仓库「管理 → 基本信息」把 **默认分支** 改成 `opensource`。

## 5. 仓库设置（Gitee · 私有）

- **默认分支**：`opensource`（管理 → 基本信息）。
- **私有仓库**：只有你和被邀请的成员可见；转公开前先按 §1 再核一遍历史里没有真实凭据。
- **分支保护**：保护分支是 Gitee 企业版能力，免费私有仓库没有，靠「发布线只收快照」的纪律（§9）。
- **CI**：Gitee 不执行 `.github/workflows/ci.yml`，本地 `scripts/run_tests.py` + `release.py check` 是唯一门槛（AGENTS §2）。
- **仓库标签（Topics）**：`bilibili`、`qq-bot`、`monitoring`、`windows`、`python`，方便别人搜到。

## 6. 发布版（Gitee「发行版」）

```powershell
git push origin opensource                        # 本次快照提交先上远程
git push origin v0.3.0                            # 与 VERSION 一致的 annotated tag
.\runtime\python.exe scripts\release.py build     # 产出 dist\bili-monitor-<ver>.zip + SHA256SUMS
```

在 Gitee 仓库 →「发行版」→「新建发行版」：选 tag `v0.3.0`（历史版本 `v0.1.0`），标题同 tag，
正文摘 `CHANGELOG.md` 对应小节，附件上传 zip 与 `SHA256SUMS`。

这一段（push、打包、建发行版、传两个附件）也可以一条命令做完：
`python scripts/release_gitee.py`——它会自己查 tag 是否已发过，重跑时只补没上传的附件。

包内只有可运行的项目本身，外加**自带的 Python 运行时** `runtime/`（CPython 3.12.7 x64 + 预装依赖，
解压后约 45 MB，整个 zip 约 20 MB）——正因为带上它，用户机器上不装 Python 也能「解压即用」。
`.git`、`.github`、`.venv`、`data`、`logs`、`out` 与任何真实凭据都不会进包
（`.github` 只留在仓库里给 CI 用）。

`runtime/` 不入库，由 `python scripts/build_runtime.py` 现场生成（下载官方 embeddable → 解压 →
改写 `python312._pth` → `pip --target` 预装依赖 → 冒烟）。`release.py check` 会检查
`runtime/python312.zip`（标准库本体）等关键文件是否齐全，缺一个就拒绝 build。

## 7. 之后的发版流程

1. 功能 PR 合进 `opensource`，同时更新 `CHANGELOG.md` 的 `[Unreleased]`。
2. `python scripts/release.py bump patch|minor`（自动）→ 生成新版本号与 CHANGELOG 小节；
   架构级调整或新增功能模块才用 `bump major --allow-major`（第一位只能人工加）。
3. 提一个「发版」PR，CI 绿后合并。
4. `git tag -a vX.Y.Z -m "..."` → push tag → `release.py build` → 上传 Release 附件。
   这四步（连同上一步的版本号与提交）已经串成一条命令：`scripts/release_gitee.py`
   （`--dry-run` 可先看计划），细节见 [docs/31](31-发布与交接手册.md) §11「一条命令发版」。

## 8. 不要做

- **不要**把这台机器上的 `master` 推上公开仓库：它的历史里曾有真实的 `.p0_ids.json`、本机路径与实测记录。
- **不要** force push 已发布的 tag 或分支。
- **不要**把 `BBOT.env`、`config/*.env`、`.p0_ids.json`、`data/`、`logs/`、`dist/` 提交进去（`.gitignore` 已覆盖）。
- **不要**在公开 issue 里贴凭据；`release.py check` 与 CI 只能挡住仓库内的泄漏，挡不住截图。

## 9. 两条分支怎么维护

| 分支 | 用途 | 历史 | 许可 |
|---|---|---|---|
| `master` | **开发/测试线**：日常改代码、跑测试、提交都在这条线上；真实配置、`data/`、`logs/` 只留在本机（已被 `.gitignore` 排除） | 完整历史（含 0.1.0 之前的个人版提交，tag `v0.1.0-personal`） | MIT（自 v0.1.0 起与发布线一致） |
| `opensource` | **发布线**：对外可见的快照，只接收从 `master` 同步过来、已确认的迭代 | 从一个 orphan 首提交开始，之后每次发版一条快照提交 | MIT（tag `v0.1.0` 起） |

规矩只有四条：

1. **只改 `master`**：开发、调试、提交都在开发线，测试通过再谈发布。
2. **发布线只收快照**：不要直接在 `opensource` 上改文件，否则下次同步会冲突。
3. **本机常驻分支是 `master`**：发布线历史重写后两边不再有共同祖先，同步一律按「树」操作（见下面流程），不依赖 merge。
4. **发布线与发布包都不含测试文件**：`tests/`（含 `tests/fixtures/` 的真实动态样本）与
   `scripts/selftest_*.py` 只留在开发线，快照时一律从发布树剔除；
   发布包同理——`scripts/release.py` 的 `should_pack()` 已把这两类排除在外，
   出包后可以 `python -c "import zipfile;print([n for n in zipfile.ZipFile(...).namelist()])"` 抽查。
   测试仍以 `master` 上的全量为准，发版前在开发线跑通即可。

每次确认要发版时：

```powershell
# 1) 开发线：迭代 + 自测 + 改版本号（版本号与 CHANGELOG 也留在 master）
git switch master
.\runtime\python.exe scripts/run_tests.py
.\runtime\python.exe scripts\release.py bump minor     # patch / minor 自动；major 需 --allow-major
git commit -am "release: vX.Y.Z"

# 2) 同步到发布线：一条快照提交（master 删掉的文件会一起删掉）
#    发布线不含测试文件：不进分支，用临时索引直接从 master 树写快照
$env:GIT_INDEX_FILE = "$PWD\.git\tmp-openindex"
git read-tree "master^{tree}"
git rm --cached -r -q tests
git rm --cached -q "scripts/selftest_*.py"
$snapshot = git commit-tree (git write-tree) -p (git rev-parse opensource) -m "chore(release): 发布线快照 · 不含测试文件（master vX.Y.Z）"
git update-ref refs/heads/opensource $snapshot
Remove-Item Env:GIT_INDEX_FILE
.\runtime\python.exe scripts\release.py check

# 3) 打包、打 tag（仍在 master 上，工作树不动）
.\runtime\python.exe scripts\release.py build
git tag -a vX.Y.Z -m "vX.Y.Z"

# 4) 连了远端时
git push origin opensource --tags
```

> 反向也要走一次：公开仓库收到外部 PR 并合进 `opensource` 后，先把它回流开发线
> （`git switch master && git merge opensource`，或 cherry-pick 那个 PR），否则下次快照会把它覆盖掉。
