# 发布与交接手册

> 面向「拿到这个压缩包的人」。目标：**30 分钟内**在一台全新的 Windows 电脑上跑起来，并且不依赖原作者的任何账号、路径或数据。
>
> 本文只讲「怎么装、怎么接自己的账号、怎么验收、怎么长期跑」。功能设计与历史决策见 `docs/` 下其他文档。

---

## 0. 你会得到什么

一套本地常驻的 **B 站主播监控 + QQ 通知** 系统：

- 轮询你指定的一批 B 站账号，发现「开播 / 下播 / 发动态」等事件；
- 生成卡片图，通过 **QQ 官方机器人** 主动私聊推给你（或群）；
- 自带 **Web 管理台**（默认 `http://127.0.0.1:8765`）：改监控名单、看直播状态、看事件流水、看日志、扫码登录 B 站；
- 可选 **多屏直播台**（默认 `http://127.0.0.1:8760`）：一个页面同时看多个直播间。

所有数据都落在本机 `data/`，不上传、不依赖任何云服务。

## 1. 环境要求

| 项目 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows 10 1809+ / Windows 11（64 位） | 守护、开机自启、卡片字体按 Windows 实现 |
| Python | **不需要装** | 发布包自带 `runtime\`（CPython 3.12.7 x64 + 预装依赖），解压即用 |
| 磁盘 | ≥ 2 GB 可用 | 包本体解压后约 50 MB（其中 `runtime\` 约 45 MB），zip 约 20 MB，另加数据库与卡片缓存；录播清理另算 |
| 网络 | 能访问 `bilibili.com`、`api.sgroup.qq.com` | **安装时不联网**，只有跑起来取数时才需要 |

> 包里的 `runtime\python.exe` 就是解释器本体（不是 venv 启动器），不写注册表、不改 PATH、不需要管理员权限。
> 它遵守 CPython 的 PSF License，许可证随包放在 `runtime\LICENSE.txt`。

只有在**源码仓库**里开发，才需要自己准备解释器（见 [CONTRIBUTING](../CONTRIBUTING.md)）：
先跑 `python scripts\build_runtime.py` 现场生成 `runtime\`，或自备 Python 3.10–3.12 虚拟环境。

## 2. 一键安装

解压后进入项目根目录，**双击 `install.cmd`**，或在 PowerShell 里：

```powershell
cd <解压后的目录>
powershell -ExecutionPolicy Bypass -File .\scripts\install.ps1
```

**安装全程不需要填任何东西**：不用事先准备 B 站账号，也不用先申请机器人。
装完监控台会自动打开，绑定都在页面里做（第 3、4 节）。

脚本会依次做 5 件事（**全程不联网**）：

1. 校验 `runtime\python.exe` 能跑、五个必需依赖都能 import（缺了直接报错，让你重新解压）；
2. 从 `*.example` 生成配置骨架（**已存在的文件不会被覆盖**）；
3. 创建 `data/ logs/ out/ dist/`，并用 `scripts\secure_config.py` 收紧凭据文件 ACL；
4. 运行 `scripts\preflight.py` 自检，打印「通过 / 警告 / 阻塞」；
5. **启动服务并打开监控台**：8765 端口空闲时用 `scripts\service.ps1 start` 拉起守护
   （失败则直接用 `runtime\pythonw.exe scripts\run_console.py --port 8765` 兜底），
   等端口可访问后自动用浏览器打开 `http://127.0.0.1:8765`；同时尽力拉起监控室
   （`127.0.0.1:8760`，起不来只警告）。

`install.cmd` 结束时**不会自动关窗**：成功会打印监控台地址与「接入指引」入口，失败会打印退出码，
都停在那里等你按任意键。

常用参数：

| 参数 | 作用 |
|---|---|
| `-SkipAcl` | 跳过 ACL 收紧（非 NTFS 或权限受限时用） |
| `-SkipCheck` | 跳过最后的自检 |
| `-SkipStart` | 只装不启动（想自己控制何时开服务时用） |
| `-NoOpen` | 启动服务但不自动打开浏览器 |
| `-Port 8765` | 换监控台端口 |

> 老版本的 `-Python` `-NoVenv` `-Mirror` `-Force` 仍然接受，但只打印一行「已忽略」——
> 现在既没有虚拟环境，也没有要下载的东西。

装完再自查一遍：

```powershell
.\runtime\python.exe scripts\preflight.py
```

**退出码**：`0` 全绿；`1` 有阻塞项（必须先修）；`2` 自检自身异常。警告（WARN）不影响退出码，
常见的是「还没接账号」和「8765 端口已被占用」。

## 3. 接入你自己的 B 站账号（扫码登录）

> 绑定都在监控台里做：点顶栏「接入指引」→「去扫码登录」，或者走下面的命令行方式。
> 绑好后**采集进程会自动启动**（不需要手工开进程）。

系统读 B 站数据时**匿名也能跑**，但登录态能显著减少风控（`-352`）与空响应。**用你自己的号，不要用别人的凭据。**

### 方式 A：引导向导（推荐）

```powershell
.\runtime\python.exe scripts\setup_wizard.py --bili
```

终端会打印二维码，用 **B 站手机 App → 我的 → 扫一扫** 扫码确认。成功后写入 `config/bili.env` 的 `SESSDATA`。

### 方式 B：Web 管理台

打开 `http://127.0.0.1:8765` → 「B 站登录态」→「扫码登录」，或粘贴自己的 `SESSDATA` 兜底。保存前会先校验有效性。

### 方式 C：命令行

```powershell
.\runtime\python.exe scripts\bili_qr_login.py
```

### 注意

- `SESSDATA` **等同于账号密码**：只写在本机 `config/bili.env`，已被 `.gitignore` 排除；分享项目时**不要带上这个文件**。
- 浏览器退出登录 / 改密码会让 SESSDATA 失效，重新扫码即可。
### 方式 D：关注流凭据（推荐，动态采集默认走它）

动态采集默认是「关注流」：你的账号关注名单里的主播，然后一次请求就能拿回所有关注的新动态（29 个主播从
「29 次请求、30 多秒」变成「1 次请求、200 毫秒」）。它需要 `config/bili_follow.env` 里的 **SESSDATA + bili_jct**
（`bili_jct` 是 CSRF token，扫码时一起发下来，改密码前一直有效）：

```powershell
.\runtime\python.exe scripts\follow_feed_login.py
```

扫码后会自动把名单里还没关注的主播补上关注（**只关注、不取关**，每次动作记在 `logs/follow_sync/`）。不想用关注流也可以：
`config/subjects.json` 里把 `"mode"` 改成 `"per_user"`，或启动时加 `--poll-mode per_user`，就退回逐人轮询；
凭据不全时会自动退回并打印原因。原理、参数与回滚见 [35-关注流采集](35-关注流采集.md)。

## 4. 接入你自己的 QQ 机器人

### 4.1 申请

1. 打开 <https://q.qq.com/> 用 QQ 登录，进入「开发者中心」；
2. 创建**机器人**（个人开发者可选「私域 / 测试」形态），拿到 **AppID** 与 **AppSecret**；
3. 在「开发设置」里配置**IP 白名单**（填你本机的公网出口 IP；只在本机自用可先用沙箱环境）；
4. 在「功能配置」里开启**私聊 / 群聊**能力，并把自己（或目标群）加为可用对象。

> 官方机器人只能给「与机器人有会话关系」的用户发**主动消息**，且有额度限制。第一次必须先让对方给机器人发一条消息，才能拿到 `openid`。

### 4.2 填凭据

**方式 A（推荐、也是最直观的）：全在管理台里点**

打开 <http://127.0.0.1:8765>（或局域网里你配的地址）→ 顶部「机器人」页：

1. 填 **AppID** / **AppSecret** → 「保存并校验」，通过会显示机器人的名字；
2. 点「开始监听」→ 用**要收推送的那个 QQ 号**私聊机器人发一句话（群里 @ 它也
   可以）→ 页面自动显示抓到 openid，并写进 `.p0_ids.json`；
3. 点「重启采集进程」，让新的凭据与 openid 生效；
4. 在「发一条测试消息」里点发送，手机收到就说明整条链路通了。

同一页还有「清除 openid」和手动粘贴 openid 的兜底入口；所有动作等价于下面的
命令行，只是少开一次终端。

**方式 B（命令行）**

```powershell
.\runtime\python.exe scripts\setup_wizard.py --qq
```

向导会写入 `BBOT.env`：

```ini
QQBOT_APP_ID=你的AppID
QQBOT_APP_SECRET=你的AppSecret
BBOT_PUSH_AT=08:10
```

`BBOT_PUSH_AT` 只是默认值／兜底：日程表页顶部「每日推送」卡片可以把时间存进库（`meta['daily_push_at']`），
存过之后以库为准，改完 60 秒内生效，不用重启。

### 4.3 抓 openid（必做一次）

让目标 QQ 号给机器人发一条任意消息（私聊「1」即可），然后：

```powershell
.\runtime\python.exe scripts\setup_wizard.py --ids
```

它等价于 `scripts/p0_check.py listen`：验证 token、连接官方 WebSocket、收到事件后把 `openid` 写入 `.p0_ids.json`。

> `.p0_ids.json` 是你的**个人 openid**，已在 `.gitignore` 中；发布包里只有 `.p0_ids.json.example`。

### 4.4 试发一条

```powershell
.\runtime\python.exe scripts\p0_check.py token      # V1 鉴权
.\runtime\python.exe scripts\p0_check.py listen     # V2 收事件（拿 openid）
.\runtime\python.exe scripts\p0_check.py send-user "B站监控测试消息"   # V3 主动私聊
```

三步都 OK 再继续。

### 4.5 免凭据试跑

没有机器人也能验证采集链路：

```powershell
.\runtime\python.exe scripts\run_bot.py --channel echo --minutes 5```
消息只打印到控制台，不发给任何人。

## 5. 配监控名单

`config/subjects.json`（首次由 `config/subjects.json.example` 复制而来，内容是**空名单模板**）：

```json
{
  "subjects": [
    { "uid": 123456, "room_id": 654321, "name": "示例主播", "group": "默认", "enabled": true }
  ],
  "poll": { "live_interval_s": 45, "dynamic_interval_s": 240 }
}
```

三种加人方式：

1. **Web 管理台** → 「名单」→ 添加（推荐）；
2. 手改 JSON 后重启；
3. 按名字批量解析：

```powershell
# names.txt 每行一个主播昵称
.\runtime\python.exe scripts\import_by_names.py --names-file names.txt```

`live_interval_s` 建议 ≥ 40 秒，`dynamic_interval_s` 建议 ≥ 180 秒，太激进会触发风控。

## 6. 启动

现在的进程分成三个（详见 [docs/12](12-Web管理台.md) §26）：

| 进程 | 启动方式 | 什么时候在跑 |
|---|---|---|
| 监控台主进程 `scripts/run_console.py` | 安装脚本 / `service.ps1 start` / 自启 | 一直在，只服务页面与托管下面两个 |
| 采集进程 `scripts/run_bot.py --collector` | 监控台自动拉起 | 绑上 B 站账号后自动启动 |
| 推送进程 `scripts/run_pusher.py` | 监控台自动拉起 | 绑上 QQ 机器人后自动启动 |

两个后台进程默认关闭，条件消失（例如清空了 SESSDATA）会自动停。进程页能看到它们的状态，
也能手动启动 / 重启 / 停止；「采集 / 推送」跟着绑定状态走的模式叫 `auto`。

### 前台试跑（只采集，不推送）

```powershell
.\runtime\python.exe scripts\run_bot.py --collector --once    # 采一轮就退，验证能连上 B 站
```

确认能打印事件、管理台 `http://127.0.0.1:8765` 能打开，再让推送进程真发。

### 常驻 + 守护（推荐）

```powershell
# 安装并启动：计划任务优先，失败自动降级到「启动」文件夹
powershell -ExecutionPolicy Bypass -File .\scripts\service.ps1 install
powershell -ExecutionPolicy Bypass -File .\scripts\service.ps1 start

# 查看状态 / 停止 / 卸载
powershell -ExecutionPolicy Bypass -File .\scripts\service.ps1 status
powershell -ExecutionPolicy Bypass -File .\scripts\service.ps1 stop
powershell -ExecutionPolicy Bypass -File .\scripts\service.ps1 uninstall
```

守护进程 `scripts/supervisor.py` 负责崩溃重启、退避、单实例、心跳、日志轮转与优雅停止，看护监控台主进程
`scripts/run_console.py`（停止文件 `data/console.stop`，心跳 `data/console.beat`）和日程进程组
`scripts/schedule_worker.py`（停止文件 `data/schedule_worker.stop`）。采集 / 推送两个进程由监控台主进程托管，
守护不直接管。

### 可选：多屏直播台

```powershell
.\start_livedeck.bat        # 打开 http://127.0.0.1:8760
.\stop_livedeck.bat
```

## 7. 验收清单

按顺序打勾，全绿即交接完成：

- [ ] 双击 `install.cmd` 一路走完：屏幕停在「安装成功」且浏览器自动打开 `http://127.0.0.1:8765`；
- [ ] **全新机器上什么都没填就能打开监控台**——这时采集 / 推送显示「未绑定」，属正常；
- [ ] `runtime\python.exe scripts\preflight.py` 退出码 0，且「运行环境」显示**自带运行时**；
- [ ] 机器上没装任何 Python 也能跑通上面这条（绿色包的意义就在这里）；
- [ ] 首次打开看到「接入指引」，四步能一步步走完；关掉后顶栏按钮还能重看；
- [ ] 扫码绑定 B 站后，概览页「B 站登录态」显示有效，**采集进程自动变成运行中**（进程页可看到）；
- [ ] 绑定 QQ 机器人并抓到推送目标后，**推送进程自动变成运行中**；
- [ ] 管理台「动态采集方式」显示「关注流」且「最近一轮」有页数/条目（退回逐人轮询也能用，但先看原因）；
- [ ] 进程页的 `live`/`dynamic` 归属采集进程、`dispatch`/`qq_inbox` 归属推送进程，状态与实际一致；
- [ ] 机器人页「发送测试消息」能收到一条 QQ；
- [ ] 常驻 30 分钟后 `logs/` 无连续 ERROR（采集看 `logs/collector-<日期>.log`，推送看 `logs/pusher-<日期>.log`）；
- [ ] 重启电脑后守护自动拉起监控台，事件不重复推送（幂等）。

## 8. 日常运维

| 场景 | 做法 |
|---|---|
| 看运行状态 | 管理台首页 / `scripts/run_report.py` |
| 看日志 | 管理台「日志」四维筛选，或 `logs/` 按天文件 |
| 改名单 | 管理台「名单」，热生效 |
| 全站暂停 | 管理台总开关 `off`（不采集）/ `collect`（只采集不推送） |
| 推送失败 | 管理台「死信」重投；或 `scripts/push_alert.py check` |
| 清理缓存 | 停服后直接删 `data/cache/`、`data/avatars/`（会自动重建） |
| 改定时推送 | 管理台「日程表」页顶部「每日推送」卡片；没开管理台时改 `BBOT.env` 的 `BBOT_PUSH_AT`（兜底） |
| 动态采集方式 | 管理台「动态采集方式」卡可切关注流/逐人轮询、手动触发取流/补漏/同步关注；细节见 [35](35-关注流采集.md) |
| 采集/推送没在跑 | 先看绑没绑：没绑 B 站账号采集不起，没绑 QQ 推送不起（进程页那行会写「未绑定」）；绑了还不起，看 `logs/collector-<日期>.log` / `logs/pusher-<日期>.log`，或在进程页「重启」一次 |
| 看三个进程 | 进程页；或 `service.ps1 status`（会打印采集/推送状态与绑定状态），原始状态在 `data/stack.json` |
| 不让某个进程起来 | 进程页点「停止」（记为手动 off，条件变化也不会自动起），恢复点「自动」 |

数据都在 `data/bot.db`（SQLite，WAL）。备份时**连同 `data/bot.db-wal`、`data/bot.db-shm` 一起复制**，或先 `stop` 再复制。

## 9. 升级与回滚

本项目用 **语义化版本** + `CHANGELOG.md`：

```powershell
.\runtime\python.exe scripts\release.py show     # 当前版本
```

升级步骤：

1. `service.ps1 stop` 停服；
2. 备份 `data/` 与 `config/`；
3. 覆盖代码与 `runtime/`（**不要覆盖** `config/`、`data/`、`BBOT.env`、`.p0_ids.json`）；
4. 重新跑 `install.cmd`（会校验新包里的 `runtime/` 与配置模板，缺文件当场报错）；
5. 看 `CHANGELOG.md` 的「升级提示」，必要时执行迁移；
6. `service.ps1 start`，跑一遍第 7 节验收。

> **0.3.3 起进程结构变了**：守护拉起的是 `scripts/run_console.py`，采集 / 推送由它托管。
> 从 0.3.2 升级后必须 `service.ps1 stop` 再 `start`（自启脚本 `service_start.cmd` 也会被重写），
> 否则还在跑旧的单进程 `run_bot.py --web`——那个管理台没有进程托管能力，`/api/stack` 会提示
> 「当前进程由 run_bot.py --web 启动」。

回滚 = 用备份的整个项目目录覆盖回去，再 `service.ps1 start`。数据库 schema 只向前迁移，**回滚前请用 2 中的备份还原 `data/`**。

## 11. 版本策略

- 版本号唯一来源：仓库根目录 `VERSION`（`shared/version.py` 读取，`scripts/preflight.py` 与发布包校验都引用它）；
- 起点是 `0.1.0`（首个可交付版本；它原先记为 1.0.0，2026-11-08 重新编号）；
- `CHANGELOG.md` 按 Keep a Changelog 维护，`[Unreleased]` 累积下次变更，**每个版本必须留一节文字记录**。
- 这套规则同时也是项目的底层要求，写在根目录 [AGENTS.md](../AGENTS.md) §1；本节与它冲突时以 AGENTS.md 为准。

### 数字怎么涨

| 位置 | 谁改 | 什么时候递增 | 例子 |
|---|---|---|---|
| 第一位 `major` | **只能人工** | 整个项目架构级调整，或新增功能模块 | 换成全新存储层 / 新增独立子产品 |
| 第二位 `minor` | 自动 | 多个重要功能统一合并迭代时 | 「Harness 交接 + 关注流替换」合成 0.2.0 |
| 第三位 `patch` | 自动 | 缺陷修复、细节优化、未合并的小改动 | 页面不刷新、下拉不落盘 |

**低位归零**：涨哪一位，就把它右边的位全部清零。

| 起点 | 命令 | 结果 | 说明 |
|---|---|---|---|
| `0.1.1` | `bump minor` | `0.2.0` | 第三位不跟着带过去，`0.2.1` 是错的 |
| `0.9.4` | `bump major --allow-major` | `1.0.0` | 第二位、第三位一起清 |
| `0.2.0` | `bump patch` | `0.2.1` | 只有第三位原位加一 |

`bump` 已按这张表实现（`0.1.1` 升第二位得 `0.2.0` 是写死在代码里的，不是靠人记）。

`release.py` 按规则把关：`bump patch` / `bump minor` 直接生效；`bump major` 必须显式加
`--allow-major`，否则拒绝执行（退出码 2）。

### 发版

```powershell
.\runtime\python.exe scripts\release.py bump patch   # 或 minor；major 需 --allow-major
# 把这一版的改动写进 CHANGELOG 的新小节（新增/变更/修复/安全/升级提示）
.\runtime\python.exe scripts\release.py check        # 密钥扫描 + 缺件检查
.\runtime\python.exe scripts\release.py build        # 产出 dist/bili-monitor-<ver>.zip + SHA256SUMS
git tag v<ver>
```

`release.py check` 会拒绝构建包含 `SESSDATA`、`QQBOT_APP_SECRET`、`openid`、写死本机路径的文件——**发版前必须为绿**。

### 一条命令发版

上面这套（提交版本号 → tag → 发布线快照 → 打包 → 推送 → 建 Gitee 发行版）已经串进
`scripts/release_gitee.py`，在仓库根目录一条命令即可：

```powershell
.\runtime\python.exe scripts\release_gitee.py                # 发布当前 VERSION
.\runtime\python.exe scripts\release_gitee.py --dry-run      # 只检查 + 打印计划，不写任何东西
.\runtime\python.exe scripts\release_gitee.py --bump patch   # 先涨版本号（生成小节，补完再跑一次）
```

它按固定顺序做 8 步：前置检查（`VERSION` 合法、`CHANGELOG` 有这一版小节且不含「待补充」、
工作树只脏了 `VERSION`/`CHANGELOG.md`、tag 没被占用）→ 全量测试 → `release.py check` →
提交 `chore(release): vX.Y.Z` → annotated tag → `opensource` 快照（临时索引，剔除 `tests/`
与 `scripts/selftest_*.py`）→ `release.py build` 并核对 `dist/SHA256SUMS` → 推送 与 Gitee
发行版（含 zip 与 SHA256SUMS 附件）。

- 退出码：0 成功、1 执行失败、2 前置条件不满足；中途失败修完直接重跑，已完成的步骤会跳过
  （已提交的不再提交、tag 已指向 HEAD 就跳过、发行版按附件名字跳过已上传的文件）。
- 如果失败发生在**最后一步**（tag 与分支都已推上 Gitee，只有网页上的发行版没建出来），之后为了让修好的
  脚本进包又补了提交，重跑会被「tag 不等于 HEAD」拦住。这时加 `--resume`：它要求 tag 在 HEAD 的历史里、
  工作树干净，远端标签与发布快照仍对应本次发版。脚本核对 `dist/` 现有包的 `SHA256SUMS`，
  然后用原标签的发布说明补建发行版和附件。若推送阶段尚未完成，先检查远端各引用的状态。
- 令牌按 `--token-file` > 环境变量 `GITEE_TOKEN` > `~/.dsh/secrets/gitee.env` 的顺序找，
  任何输出都不打印它；没有令牌（或只想在本地出包）加 `--no-release`，不推送加 `--no-push`。
- 发布公告要自己写稿时用 `--body-file out\发布公告-X.Y.Z.md`；不传就摘 `CHANGELOG` 该版小节，
  标题默认取小节标题里「—」后面的副标题。
- 交互终端里会先打印计划再要求确认 `y`；脚本或 CI 里加 `--yes`。

### 发布在线增量包

1. 发布维护者在已配置私钥保护的位置生成至少 2048 位的 RSA 密钥。Windows PowerShell 可使用 `[System.Security.Cryptography.RSACryptoServiceProvider]` 的 `ToXmlString($true)` 导出私钥，`ToXmlString($false)` 导出公钥。私钥存放在受保护的发布环境，禁止入库或上传。
2. 首次发布支持在线更新的完整发行包时，运行 `python scripts/release.py build --update-public-key 公钥路径`。通过 `release_gitee.py` 发布时可设置环境变量 `BILI_UPDATE_PUBLIC_KEY`。已使用旧版的用户需一次性安装这个完整发行包。
3. 以后用同一公钥生成目标完整包，保留基线完整包，再运行 `python scripts/build_delta.py --base 旧版.zip --target 新版.zip --sign-key 私钥路径`。将生成的 `bili-monitor-update-旧版-新版.zip` 上传到目标版本的 GitHub Release 附件。有多个受支持的起始版本时，分别生成附件。
4. 运行时、依赖、受保护的守护脚本、SQLite 存储层或周表存储层发生变更时使用完整发行包。更新只接受同一签名密钥，换钥时也需要重新安装完整发行包。若本地代码文件有改动，校验会拒绝覆盖。

测试实际发布时，用临时安装目录确认设置页可以从 GitHub 取得附件、校验、切换并重新打开管理台。保留原完整包供离线恢复。
