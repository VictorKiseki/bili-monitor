# 录播自清理（Recorder Cleanup）

首次使用时，在监控台「录播清理」填写已存在的录像目录并保存，再按需启用自动清理。目录留空时无法扫描或启动。

## 背景

目标：给录制目录设一个总大小上限，超过后**先通知、再删最旧**；同时保证绝不删正在录制的文件，也不碰剪辑目录。

## 为什么不做进录播姬

- 录播姬是闭源分发的 .NET 8 WPF 程序。改 UI 或核心要 fork 上游（GPL-3.0）并长期跟进，维护成本高于收益。
- 录制时它对 FLV 持有写句柄；外部清理只要跳过"被占用/最近修改"的文件就是安全的。
- 独立脚本不依赖录制进程：录播姬或 bot 崩了，自启循环照样能按计划检查。
- 因此采用**外部管理器 + 登录自启循环**，不改上游二进制。这与 [录播功能并入评估](19-录播功能并入评估.md) 的"进程级 sidecar"结论一致。

## 流程（2026-11-02 改版）

1. **按天调度**：每 `interval_days` 天的 `run_time`（HH:MM）检查一次。守护把 `next_run_at` 写进 `logs/recorder_cleanup_schedule.json`，重启后继续用；改了间隔或时间会重置。
2. **只生成计划，不直接删**：扫描受管房间目录，按 mtime 从旧到新选出"删到不超上限且磁盘不低于保底"所需的最少文件，写成 `logs/recorder_cleanup_review.json`，状态 `awaiting_notify`。
3. **Bot 通知**：采集进程 `scripts/run_bot.py` 的清理通知循环发现待确认计划后，用**监控台自己的 QQ Bot** 推送候选清单（文件多时自动分多条，编号连续）。只有全部发送成功才写 `logs/recorder_cleanup_notify.json` 的 `status=sent`。
4. **1 小时确认窗口**：守护看到 `sent` 才开始倒计时（`deadline_at = sent_at + review_wait_minutes`）。通知没发出去、发送失败、Bot 没运行，都**不会开始倒计时，也绝不会删除**。
5. **用户回复**：在 QQ 私聊回复 `保留 1 3`、`保留 1-3` 或 `全部保留`，Bot 写入 `logs/recorder_cleanup_decisions.json`。只接受 `.p0_ids.json` 里的 owner openid；过期计划拒绝修改。
6. **到点执行**：先移动保留项到保护目录（默认 `root/_protected`，按房间子目录存放，重名自动加时间戳），移动成功才从待删列表移除；其余候选删除 `.flv` 和同名 `.xml`。移动失败的文件**绝不删除**，计划保持 `executing` 等下一轮重试。
7. **收尾**：全部候选进入终态后计划 `done`，归档到 `logs/cleanup_reviews/<plan_id>.json`，删除/保护数量写进状态文件。

## 清理规则

2. 受管目录内**所有文件**都计入 `total`（不只 FLV，避免剪辑素材把盘吃满却统计不到）；待删候选只取 `.flv`，以及同名 `.xml` 弹幕。
3. 候选按 mtime 从旧到新排序；选中时按 `.flv + 侧车` 的总大小递减预算。
4. 三重安全阀：
   - 最近 `keep_recent_minutes`（默认 30）分钟内修改过的 FLV 或 XML 跳过；
   - `os.open(path, O_RDWR)` 拿不到句柄（被视为仍被占用）跳过；
   - 达到 `total <= max_bytes` **且** `free >= min_free_bytes` 就停止选择。
5. 删除失败（占用/权限）最多重试 3 次，之后标记 `skipped`，不会无限重试。
6. **确认后是永久删除，不进回收站。** 想先看清单用 dry-run：不建计划、不通知、不删除。
7. 单实例锁 `logs/recorder_cleanup.lock`：守护运行时，手动 `--once` 会跳过，不会并发删除。

## 配置

`config/recorder_cleanup.json`（缺失时自动生成）：

```json
{
  "root": "",
  "max_gb": 100,
  "min_free_gb": 20,
  "keep_recent_minutes": 30,
  "interval_days": 1,
  "run_time": "03:00",
  "review_wait_minutes": 60,
  "protected_dir": "",
  "enabled": false,
  "managed_dir_pattern": "^\\d+-",
  "sidecar_suffixes": [".xml"],
  "log_file": "logs/recorder_cleanup.log",
  "dry_run": false
}
```

| 字段 | 说明 |
| --- | --- |
| `root` | 初次使用需在监控台填写已存在的录像目录。直接改配置时也支持相对项目根的路径。 |
| `min_free_gb` | 磁盘剩余保底，默认 20；`0` 表示不启用 |
| `keep_recent_minutes` | 最近修改保护窗口，默认 30 分钟 |
| `interval_days` | 每几天检查一次，1-365，默认 1 |
| `run_time` | 检查时刻 HH:MM，默认 `03:00` |
| `review_wait_minutes` | Bot 通知后等待确认的分钟数，默认 60 |
| `protected_dir` | 保留文件移动目标；空表示 `root/_protected` |
| `enabled` | 自动清理总开关；`false` 时守护启动后立即退出 |
| `managed_dir_pattern` | 房间目录正则，默认 `^\d+-`；不要放宽到匹配所有目录 |
| `sidecar_suffixes` | 随 FLV 删除的侧车后缀，默认 `[".xml"]` |
| `log_file` | 相对项目根；RotatingFileHandler，2MB × 3 |
| `dry_run` | 全局 dry-run 开关；命令行 `--dry-run` 优先 |

> 旧版的 `interval_s` 字段仍能读，但已不再参与调度；保存一次配置后会保留原值，新逻辑只看 `interval_days` + `run_time`。

## 状态与文件

| 文件 | 作用 |
| --- | --- |
| `logs/recorder_cleanup_status.json` | 守护 phase、last_run、last_review、last_error |
| `logs/recorder_cleanup_review.json` | 当前待确认计划（候选、编号、状态、截止时间） |
| `logs/recorder_cleanup_notify.json` | Bot 发送结果（sent/failed、sent_at、message_id） |
| `logs/recorder_cleanup_decisions.json` | 用户保留决定（按 plan_id 隔离） |
| `logs/recorder_cleanup_schedule.json` | 下次检查时间与配置指纹 |
| `logs/recorder_cleanup_run.request` | 管理台「立即检查」的触发文件 |
| `logs/cleanup_reviews/<plan_id>.json` | 完成计划的归档 |
| `root/_protected/<房间>/` | 用户标记保留的录像与同名弹幕 |

## 用法

```bash
python scripts/recorder_cleanup.py --show              # 看占用/上限/下次检查/保护目录
python scripts/recorder_cleanup.py --once --dry-run    # 只打印会删哪些，不建计划
python scripts/recorder_cleanup.py --once              # 检查一次：只创建待确认计划
python scripts/recorder_cleanup.py --set-max-gb 120    # 改上限并写回配置
python scripts/recorder_cleanup.py --loop              # 常驻，按天+时间调度
python scripts/recorder_cleanup.py --stop              # 给常驻实例写停止标记，让它自己退出
```

- `--once` 是默认行为；非 dry-run 时只建计划，等 Bot 通知和 1 小时窗口，**不会立刻删**。
- `--max-gb` 只临时覆盖本次，不写回；`--set-max-gb` 写回。
- `--loop` 启动时先删残留的 `logs/recorder_cleanup.stop`，再检查 `enabled`；`enabled=false` 时只写状态就退出。
- `--loop` 里 `dry_run=true` 只预览并推进调度，不建计划、不通知、不移动、不删除。
- `--show` 会调用 `ensure_schedule`，因此可能顺手写入/刷新 `next_run_at`。
- 输出统一 UTF-8，日志同时写文件和 stdout（自启用 `pythonw.exe` 时只写文件）。

## 自动运行

- 启动项：`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\BililiveRecorderCleanup.lnk`
- 目标：`.\runtime\pythonw.exe`
- 参数：`"<项目目录>\scripts\recorder_cleanup.py" --loop`
- 工作目录：`<项目目录>`
- 行为：登录后启动，按 `interval_days` + `run_time` 调度；若登录时已经过了本次时间，会立即补一次；`pythonw.exe` 无窗口。
- 安装/修复：`powershell -ExecutionPolicy Bypass -File scripts/install_cleanup_autostart.ps1`（脚本会先检测已有实例，避免重复启动）。
- 若配置 `enabled=false`，安装脚本只建快捷方式、不拉起守护；下次登录也不会启动，直到在管理台重新启用。

验证：

```powershell
Get-CimInstance Win32_Process -Filter "Name='pythonw.exe'" |
  Where-Object { $_.CommandLine -like "*recorder_cleanup.py*" } |
  Select-Object ProcessId, CommandLine
Get-Content <项目目录>\logs\recorder_cleanup.log -Tail 30
```

注意：

- 必须登录后才会跑；录播姬 WPF 也是登录自启，二者场景一致。若以后要"未登录也跑"，需要管理员权限注册服务或计划任务。
- 管理台点「停止守护」不靠杀进程：写 `logs/recorder_cleanup.stop`，循环每秒检查后自行退出；`logs/recorder_cleanup.lock.info` 里的 PID 只用于显示/存活判断。
- 锁文件本体只做互斥（Windows 字节锁会让别的进程读不了），PID/角色写在旁边的 `logs/recorder_cleanup.lock.info`：`daemon` / `once` / `manual`。管理台只把 `daemon`（以及旧版只有 PID 的锁文件）当作守护，避免把控制台自己的手动任务误判为常驻进程；退出时会清空锁文件并删除 `.info`。
- `G:` 必须是本机盘。若是网络映射盘，登录会话里可能看不到，需要改用 UNC 路径并确保凭据可用。
- 脚本以当前用户权限删文件；ACL 不允许时日志记录"删除失败，跳过"。
- 单实例锁 `logs/recorder_cleanup.lock`：常驻循环运行时，手动 `--once` 会打一条"另一个清理实例正在运行"并退出，不会并发删。

## Bot 确认

- 生产 Bot 由 `scripts/run_bot.py` 启动；`--no-inbox` 可关闭入站（此时只能看通知，不能回复保留）。
- 入站 WebSocket 只处理 `C2C_MESSAGE_CREATE`，且必须匹配 `.p0_ids.json` 的 `user_openid`；其他人发命令无效。
- 命令词：`保留`、`保护`、`不清理`、`不可清理`、`拒绝`、`别删`；支持空格/逗号/顿号/范围 `1-3`；`全部保留` 表示保护本次全部候选。
- 编号以通知里的 `1. 房间/文件名` 为准；计划结束后编号失效。
- 通知发送失败会按 60 秒（普通错误）或 300 秒（openid/权限）重试，**失败期间不倒计时**。

## 管理台（推荐日常使用）

Web 管理台「录播清理」页签，开关、设置、状态、操作、日志、登录自启都在这里：

| 区域 | 能力 | 接口 |
|---|---|---|
| 状态卡 | 守护运行/PID/运行时长、自动清理开关、下次检查、待确认、上限/保底、磁盘剩余、上次清理、保护目录 | `GET /api/cleanup/status` |
| 开关 | 启用/停用自动清理；停用会写 `enabled=false` 并让守护退出 | `POST /api/cleanup/enable {enabled}` |
| 设置 | 首次填写录像目录，设置上限、磁盘保底、保护时间、检查频率及 dry-run。保护目录只读 | `GET/PATCH /api/cleanup/config` |
| 待确认清理 | 当前计划、原因、候选编号/文件/大小/时间/状态、截止时间、已保留编号 | `GET /api/cleanup/status` 的 `review` |
| 操作 | 立即扫描（dry-run）、立即检查并通知、启动/停止/重启守护 | `POST /api/cleanup/scan`、`/run`、`/start`、`/stop`、`/restart` |
| 登录自启 | 加入/移除启动项；加入时调用 `scripts/install_cleanup_autostart.ps1` | `POST /api/cleanup/autostart {enabled}` |
| 日志 | 按级别/关键字筛选，3 秒自动刷新 | `GET /api/cleanup/logs?lines=&level=&q=` |

边界：

- 「立即扫描」始终 dry-run，只读，不会建计划。
- 「立即检查并通知」不直接删：守护没在跑会先拉起，再写触发文件；有活动计划时只提示，不重复创建。
- 「停用自动清理」会让守护在下一轮退出；待确认计划保留，但不会继续倒计时/删除。
- 设置保存后写回 JSON；守护每轮重读，间隔/时间在下一轮调度生效。
- 状态来自 `logs/recorder_cleanup_status.json`；日志仍是 `logs/recorder_cleanup.log`。
- 管理台只监听 127.0.0.1，清理接口同样走环回校验；没有公网暴露面。

## 运维与容量

- 改计划：管理台「录播清理 → 清理设置」保存，或改 `config/recorder_cleanup.json` 后重启守护。
- 删不干净：看日志末尾 `仍未达标...`。常见原因是候选都被占用/太新，或 `total` 里非 FLV 占了大头。
- 误删风险控制：只删受管房间目录内的 `.flv`；不要放宽 `managed_dir_pattern`；不要指向非录制根目录；保护目录不要放在会被 `^\d+-` 匹配的目录下。
- 容量参考：5/10/29 人 × 3h/天 ≈ 37/75/217 GB/天。100GB 上限对 29 人约 11 小时；按实际开播密度调 `max_gb`。
- 与 `docs/19` 的关系：19 回答"要不要把录播姬并进项目"；本篇是"已经独立落地的清理能力"，二者不冲突。
